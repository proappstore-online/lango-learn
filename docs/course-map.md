# Course map contract (LNG-030)

`0005_course_map` extends the existing D1 model without changing the original course, version, lesson, release, or learner rows. Existing content and sessions keep their exact version IDs. The migration adds locale records, a course-to-locale map, ordered units, ordered lesson placements, and lesson prerequisites. The app database is isolated by PAS app; curriculum actions require the `curriculum_editor` app role and derive the actor from `:__user_id`.

Locale rows use a canonical BCP-47 language, optional script, and optional region: lowercase language, title case ISO 15924 script, uppercase two-letter or three-digit region. `create_course_locale` canonicalizes case on the server and preserves script and region. Thus `en-Latn-US`, `en-Latn-GB`, and `en` are distinct. This first schema supports the language[-script][-region] subset; variants and extension subtags require a later additive contract. A course map points to two existing locale rows. Its language subtags must match the legacy `courses.source_language` and `target_language` fields. Once bound, the map and locale records are immutable; a new course shell is needed to change the language pair.

A course version owns units, and each unit places lessons from that same version at unique nonnegative positions. Existing lesson positions remain the fallback order for older snapshots. A lesson can have multiple same-version prerequisite lessons. A recursive insert guard rejects cycles, including indirect ones. Unit, placement, and prerequisite rows can be added only while the version is `draft`; they cannot be changed or deleted after insertion. Version identity and package version cannot change. The existing lifecycle remains `draft → review → approved → published → retired`, with `review → draft` for revision. A transition guard rejects skipped or backwards transitions. `course_map_release_state` derives `draft`, `published`, or `deprecated` from release history; it does not rewrite any historical release or session.

The five new staff actions follow the existing audited, transactional batch pattern. `request_id` prevents replay, `expected_updated_at` prevents stale draft writes, and a failed insert rolls back its audit row. The server validates the app role before executing SQL. `pnpm check:migrations` checks ordered, repeatable, additive migrations; `pnpm check:actions` runs all actions against fresh and upgraded persisted SQLite files and covers locale variants, malformed tags, role denial, replay, stale writes, missing references, cycles, release states, immutable versions, and audit rollback. Fixtures are synthetic and are never published course content.
