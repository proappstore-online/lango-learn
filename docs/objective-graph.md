# Objective and knowledge graph contract (LNG-031)

`0006_objective_graph` is additive to the course map. An objective and each knowledge component belong to an exact course version. The seven component kinds are objectives, lexemes, phrases, grammar points, pronunciation patterns, register tags, and confusable pairs. The six objective-to-component edge tables carry an explicit relationship type (`teaches`, `reinforces`, or `assesses`) and an order. Objective prerequisites are directed edges with recursive cycle rejection. Each table has a stable `(course_version_id, sort_order, id)` traversal order.

Every node's locale references a canonical `course_locales.tag` and must be one of its course map's source or target tags. Edges require both endpoints to share an exact version and locale. An objective may link to a lesson only in the same version. Graph insertion requires a mapped draft version. Component and edge rows are immutable; objectives may be updated only while their version is draft, with a newer server timestamp. An objective with edges cannot change locale. Published snapshots remain unchanged, and existing learner sessions keep their pinned version.

Curriculum-editor actions create all node and edge kinds, update objectives, and read a version-pinned graph. Each write is a transactional audit-first batch with a request UUID, `expected_updated_at` course-version checkpoint, and server-provided actor and timestamp. Replays, stale checkpoints, duplicates, missing references, role failures, and invalid relationships write neither graph rows nor audit rows. The graph read requires the editor role because it can expose drafts; it returns bounded keyset pages ordered by objective `(sort_order,id)`, with each linked component array ordered by edge `(sort_order,id)`.

These tables define structure and synthetic test data, not approved learning outcomes or published course content. LNG-002 remains responsible for approving contextual, observable, source/target-scoped outcome definitions and evidence requirements. The later content package and release validation work can build on these relationships.

`pnpm check:migrations` verifies the SQL file matches the deploy manifest and exercises fresh, repeat, and persisted upgrade paths plus direct foreign-key, uniqueness, cycle, locale, and draft constraints. `pnpm check:actions` exercises all registered actions on fresh and upgraded persisted databases, including role denial, stale and replayed mutations, audit rollback, and deterministic graph reads.
